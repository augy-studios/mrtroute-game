# migrations

SQL for the shared uwuapps Supabase project. Paste each file into the SQL
editor and run it once, in number order.

**Never edit a file once it has been run.** Every change, to the schema or
the line data, is a new file with the next number.

| File | What it does |
|---|---|
| `001_lineorder_schema.sql` | The `lineorder_` tables, the best-per-name leaderboard view, and the rate limit, load, answer, submit and prune functions. |
| `002_lineorder_load_network.sql` | Each line's stations in order, and which are next to each other. Generated by `python scripts/seed_supabase.py --sql`; regenerate rather than edit. |
| `003_lineorder_leaderboard_totals.sql` | The total points board: a view adding up every submitted run per name, and submit returning both ranks. |
| `004_lineorder_anticheat.sql` | Times each answer, and keeps runs with more than one right answer under a second off the leaderboard. |

**Needs `mrtguessr_stations`.** Stations are read from MRT Station Guesser's
table in the same project rather than copied, as the spec asks when one
already exists. `001` stops with an error if it is missing, and the load
function refuses, changing nothing, if any station name does not match.

`002` and `python scripts/seed_supabase.py` load the same rows; use either.
Both replace the two line tables in one transaction, so a reload is safe.
After refreshing `main-site/data/`, `--sql` writes the load as the next
numbered file, leaving `002` as it was.

Every table has row level security on with no policies. Only the service role
key, used by the Vercel functions and the seed script, can read or write.
